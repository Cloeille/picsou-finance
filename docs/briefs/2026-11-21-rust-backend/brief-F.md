DELIVERABLES:
1. Crate `picsou` (edition 2024, lib + bin `picsou`), with the dependencies every track will need declared now (axum 0.8, tower-http, tokio, sqlx 0.8 postgres + rustls + chrono + uuid + rust_decimal + json, rust_decimal with exact JSON numbers via serde_json arbitrary_precision, serde_with, chrono, jsonwebtoken, bcrypt, aes-gcm, totp-rs, reqwest rustls, tracing + tracing-subscriber + tracing-appender, thiserror, include_dir, base64, rand, sha2, hmac, wiremock dev-dependency). Unknown timezone fails startup, as Java does.
3. `db`: the pool and a Flyway-compatible migrator. It embeds `backend/src/main/resources/db/migration`, applies pending versions in order with out-of-order allowed, writes `flyway_schema_history` rows exactly as Flyway 11 would (same columns, Flyway's CRC32 checksum, description, type SQL, installed_rank), fails startup when the database holds an applied version this binary lacks, and reproduces `LegacyMigrationRenumberingCallback` and anything `ReleaseMigrationCli` does at startup. Then start the Java jar on the Rust-migrated database and confirm Flyway validation passes.
4. `error`: `AppError` and its ProblemDetail rendering, identical to `GlobalExceptionHandler` for every case it handles (including validation 422 with the `errors` map, malformed JSON, unknown route, method not allowed, payload too large).
5. `auth` and `http`: JWT (same claims, `tv` token-version check), the session cookies with the same names and attributes, the remember-me persistent-token flow, the setup gate, cross-site CSRF rejection, anonymous body limit, client IP with trusted proxy, per-IP rate limiting with named buckets equivalent to `RateLimitConfig`, dynamic CORS, security headers including CSP and optional HSTS, response compression, the SPA with index.html fallback, Bearer authentication for personal access keys (`AccessKeyAuthFilter`). Expose a typed extractor that gives handlers the authenticated user, the effective member id (with the admin impersonation override), the auth method (cookie, access key with its scopes, OAuth token) and the role. Design a hook so track T1 can plug OAuth2 bearer validation and SSO without editing your files.
6. `crypto`: `CryptoEncryption` byte-compatible (a value encrypted by Java decrypts in Rust and the reverse, tested with a vector produced by the Java code), plus `SecretBootstrap` (same files, same permissions).
7. `actuator`: `/actuator/health`, `/actuator/health/liveness`, `/actuator/health/readiness`, `/actuator/info` with the same bodies (find where `app.desktop` and `app.desktop-unavailable` come from).
8. `setup_auth`: SetupController, AuthController, MfaController, SessionController, every endpoint, every edge case, with their services ported (login timing-attack protection included).
9. `routes`: a route registry every module uses to register its routes, so a test can list (method, path) pairs. A test compares them with `backend-rs/scripts/java_endpoints.tsv`: it fails on any Rust route not in the Java list, prints coverage, and with `PICSOU_REQUIRE_FULL_COVERAGE=1` fails on any Java route missing. Translate Spring path variables (`{id}`) and patterns consistently.
10. Module skeleton: one module per track per `plan.md` (`identity`, `admin`, `ledger`, `accounts`, `family`, `budget`, `wealth`, `market`, `sync`, `connectors`, `transfer`, `jobs`, `mcp`, `ai`), each a directory with a `mod.rs` exposing its router (empty for now) and already wired into the app, plus one test file per module under the single integration test binary, so later tracks never edit `lib.rs`, the app router or the test entry point.
11. `clock` (injectable, fixed in tests) and `testing::TestApp`: spawns the app in-process on a fresh database cloned from a template migrated once per test run, with helpers to complete setup, create members, log in and send requests with cookies or bearer keys, and to point any external base URL at a wiremock server.
12. A test that fails when `f32` or `f64` appears in `src/` outside an explicit allow-list (empty now).
13. `picsou::serve(config, listener) -> Result<()>` with graceful shutdown, used by `main.rs`; tracing to stdout, plus a size-bounded rolling file when a log directory is configured. Log the time from process start to readiness.
14. `backend-rs/README.md`: build, run, test, layout, how a track adds a domain. Short.

# Standing orders (Rust backend program)

Every agent in this program obeys these lines. They override anything a brief leaves unsaid.

1. Work only in the worktree and branch your brief names. Never push, never fetch-and-merge, never touch a remote, never open a pull request, never rebase or force anything.
2. The Java backend under `backend/` and the notes under `docs/features/` are the specification. Before implementing an endpoint, read its controller, the services and DTOs it uses, and its Java tests. Never guess behavior. When Java and a doc disagree, Java wins; list the disagreement in your report.
3. JSON is Jackson's: camelCase names exactly as the Java DTO, null fields omitted (`#[serde_with::skip_serializing_none]` on every response type), unknown request fields ignored, `LocalDate` as `YYYY-MM-DD`, `Instant` as RFC 3339 UTC with `Z`. Check every response type against `frontend/src/types/api.ts` and the relevant `frontend/src/features/*/api.ts`.
4. Money, quantities, prices, rates and percentages are `rust_decimal::Decimal` end to end, from SQL `numeric` to JSON number. Never `f32`/`f64` for them, not even transiently. Reproduce Java's `BigDecimal` scale and `RoundingMode` exactly where Java sets them.
5. Errors go through `picsou::error::AppError`, which renders the same RFC 7807 bodies as `GlobalExceptionHandler` (status, title, detail, optional stable `code`, `errors` map on validation). Never expose SQL errors, stack traces, internal names or upstream bodies.
6. Every query is scoped to the authenticated member exactly as the Java repository call is. Family sharing and admin impersonation go only through the helpers in `picsou::auth`.
7. Logs never contain a password, token, cookie, TOTP secret, private key, full IBAN or account number, or a bank credential.
8. Tests assert behavior over HTTP through the in-process router (`picsou::testing::TestApp`), on a fresh database the harness creates. Time comes from the injected `Clock`; no test depends on the current date. External HTTP (banks, prices, sidecars, AI) is stubbed with `wiremock`; tests never reach the internet. Port the meaningful cases of the Java tests for your scope, edge cases first (rounding, member isolation, co-ownership, hidden and child accounts, errors).
9. Test database: PostgreSQL 16 at `127.0.0.1:55432`, user `picsou`, no password (trust). The harness creates and drops uniquely named databases. Never drop a database you did not create. Never stop that server.
10. Before reporting done: `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings` and `cargo test` all pass in `backend-rs/`. Paste the summary lines in your report.
11. No dead code, no placeholder data, no silent stubs. An endpoint you cannot finish answers 501 with a ProblemDetail `code` of `NOT_IMPLEMENTED` and is listed in your report with the reason.
12. Comments only for a non-obvious why. All code, comments, docs and commit messages in English. Conventional commits (`feat(rust): ...`) on your branch; commit as you go.
13. Edit only the paths your brief puts in scope. If you need a change in a shared module, make the smallest additive change, and list it under "shared changes" in your report.
14. Use `cargo add` for dependencies so versions are current; prefer crates already in `backend-rs/Cargo.toml`.
15. Your final message is the report, at most 60 lines: status (done / partial / blocked), branch, head SHA, endpoints implemented (count and list of any 501), tests added and the verify summaries, shared changes, deviations from Java and why, open follow-ups. Write a longer report to the path your brief gives if you need more room.
